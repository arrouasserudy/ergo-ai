# Otio — assistant for pediatric occupational therapists

- Code is written in English: identifiers, files, routes, DB columns, enum/tag keys, and comments.
- UI copy lives only in the dictionaries: `src/i18n/fr.ts` (default, source of the `Dictionary` type) and `src/i18n/he.ts` (Hebrew, RTL). Every key must exist in both (the type enforces it). Never put UI strings in components.
- Read copy with `await getI18n()` in server components/pages and `useI18n()` in client components; both give `t` plus locale-aware helpers (`date`, `dateTime`, `age`, `tag`, `cause`, `situation`, `error`). Validation and actions return error codes (`required`, `tooLong:200`…), translated at display.
- RTL: use logical Tailwind classes (`ps-/pe-/ms-/me-/start-/end-/text-start`), `rtl:rotate-180` on directional arrows, `dir="auto"` on user-typed inputs, and `<bdi>`/`isolate()` around child names inside translated text.
- Children are stored by name (`children.name`: full name or initials, as the therapist types it). The name is never sent to an AI model: prompts and child context stay pseudonymized.
- Multi-tenancy: children belong to an `account` (a cabinet); `therapists` (Better Auth users) belong to one account and see all its children. Every page and server action must call `requireTherapist()` (`src/lib/session.ts`) and scope queries by `accountId`. Owner-only actions use `requireOwner()`.
- Auth: Better Auth email/password (`src/lib/auth.ts`). Public sign-up endpoint is disabled; therapists are created only via `createTherapist()` (`src/lib/therapists.ts`).
- Stack: Next.js 16 App Router, Tailwind v4 (tokens in `src/app/globals.css`), Drizzle + SQLite (`data/ergoai.db`, auto-migrated on startup).
- After a schema change: `pnpm db:generate`. Seed demo data: `pnpm db:seed [--reset]`.
- Checks: `pnpm typecheck && pnpm lint && pnpm test && pnpm build`. Unit tests live next to pure logic (e.g. `src/lib/episode-insights.test.ts`).
- Reports module (`/reports`, `src/lib/reports/`): session notes (typed, or dictated: `POST /api/reports/transcribe`, OpenAI `gpt-4o-transcribe`, audio never stored) → one generic structured draft, written for parents (recipient `parents`; older reports may also hold `doctor` / `school` versions), in `report_variants` (`generated` = model output, `sections` = edited text). Generation is one structured-output call per recipient (Claude, else OpenAI) via `generate.ts`; prompts in `prompt.ts` (pure, tested). The model never sees the child's name: it writes `{{child}}`, replaced by the name server-side. Validating an edited version stores a `style_examples` pair (draft → corrected), replayed in later prompts with the child's name swapped back to `{{child}}`. The editor shows the exact prompt (`previewReportPrompt`) and warns when the child's name appears in the notes (`findChildName`, not replaced). Export (PDF via print, Word via `docx`, copy) runs in the browser; an optional first name typed at export replaces the child's name client-side (`text.ts`) and is never sent or stored. Letterhead lives on `accounts.letterhead`.
- Resources: one sidebar item (`/resources` → `/forms`) groups Forms, OT tests and the library, which keep their URLs; `ResourcesTabs` (in each section's `layout.tsx`) switches between them.
- Forms module (`/forms`, under Resources, `src/lib/forms/`): a blank questionnaire (PDF sent as-is, Word via `mammoth` → HTML) is converted by one structured-output call (`convert.ts`, `generateStructured` in `reports/generate.ts`) into the JSON convention of `schema.ts` (sections of typed fields; ids assigned by `normalize.ts`, never by the model), then edited and published in `FormBuilder`. `child_forms` copies the schema when a form is attached to a child; answers (`answers.ts`: sanitized against the schema, keyed by field id) are filled in the app or by parents through a public link `/f/[token]` (no session; only the token's sha256 is stored; 30 days; excluded in `proxy.ts`; the child's name is never shown there). Completed forms can be attached to a report (`reports.form_ids`): their answers go into the prompt with the child's name replaced by `{{child}}`. `FormRenderer` renders every mode (fill, read-only, print). A published form can be *auto* (added to every active child and to new ones by `syncAutoForms` in `auto-assign.ts`: on template/child/settings changes and once a day from the `(app)` layout) and have a yearly deadline (`MM-DD`, due once per school year from `accounts.school_year_start`; one copy per child per `cycle`, enforced by a unique index). Due-date rules live in `deadlines.ts` (pure, tested): orange within `accounts.deadline_warn_days`, red when overdue, shown on the child (list, page, forms card) and in the bell (`NotificationBell`, fed by `pendingForms` in the layout). Settings → "Forms and deadlines" is per cabinet. Built-in forms (`forms/defaults/`, one file each with a `key` and `version`) are ensured in every cabinet by `ensureBuiltinForms` (`builtin.ts`: at startup, on sign-up, in the seed): published, not editable or deletable; bump `version` to push new content to all cabinets.
- OT tests module (`/assessments`, under Resources, `src/lib/assessments/`): standardized tests written by hand, one file per test in `definitions/` (content in the test's own language + a pure `score()` built from `scoring.ts`), listed in `registry.ts`; each definition has a test checking it against the paper form (item lists, maxima, ranges). Item kinds: `rating` (a value of the section's scale, e.g. Sensory Profile 2) and `level` (behaviors ticked per age level, the most ticked level suggested, e.g. Knox). An administration (`assessments` table) stores sanitized answers (`answers.ts`) and, once completed, a snapshot of the scores (drafts are scored live); `definitionVersion` records the definition used. The AI never computes a score. Tests with `respondents` including `parent` can be sent through a public link `/t/[token]` (same token scheme as `/f/`, excluded in `proxy.ts`; items only, never scores or the child's name). Completed tests can be attached to a report (`reports.assessment_ids`): only the computed scores go into the prompt (`prompt.ts`), never answers or comments.
- Home (`/`, `src/app/(app)/page.tsx`, `src/lib/dashboard/`): a light dashboard, the landing page after login. Four counts (active children, draft reports, forms due, crises in 7 days), an open-episode banner, a "to do" list (overdue forms, forms due soon, drafts; ordered by `sortTodo` in `feed.ts`, pure, tested) and recent activity (closed episodes, filled-in forms, completed tests). No AI. Two optional cards, each hideable per therapist (`therapists.hide_week_streak` / `hide_setup_guide`, Settings → My account): the "up to date" week (`streak.ts`, pure, tested: to-do items cleared this week, and weeks in a row ending with no overdue form and no draft older than 14 days, rebuilt from form due/submit dates and report validation dates (`closedAt` in `reports/status.ts`); paperwork only, never crises, scores or report counts) and the getting-started guide (`setup.ts`: steps detected from existing rows by `setupDone`, never ticked by hand; asking Amit is per therapist, the letterhead step owner-only).
- Events and calendar: `child_events` (kind `intake` | `parent_guidance` | `report_due` (+ `report_id`) | `other` (details required); local `date` + optional `time`), added from the child header ("Add event", `EventDialog`), listed in the overview's "Upcoming" card (`?event=<id>` opens one for editing). Pure rules in `src/lib/child-events/events.ts` (tested): a report due date is done once its report is no longer a draft, otherwise orange/red like form deadlines. The calendar (`/calendar`, `src/lib/calendar/`) shows only what is planned: these events, form due dates and birthdays, never logged items (crises, reports written, forms filled…), which stay in the child's timeline.
- Crises module: `episodes` (kind `crisis` | `difficulty`), cause catalog in `src/lib/episode-catalog.ts`, ranking/patterns in `src/lib/episode-insights.ts` (pure counting, no AI, no diagnosis). Local-time logic uses `APP_TIME_ZONE`.
- Collègue expert (Amit, `src/lib/expert/`): a floating chat bubble (`AmitBubble`, mounted in the `(app)` layout); `/expert` and `/expert/[id]` redirect to `/?amit=…`; the library is `/expert/library`, under Resources. One tool, `search_literature`, behind two chat providers (`providers/`): Claude (native `search_result` citations) and OpenAI Chat Completions (`[library:123]` markers resolved in `answer.ts` against retrieved passages only). Both produce provider-neutral `AnswerPart`s; a conversation keeps its provider (history is stored in that provider's format). Embeddings: Voyage or OpenAI (`embeddings.ts`), model recorded with the vectors and checked at search time. Retrieval = FTS5 + sqlite-vec (OpenAI `text-embedding-3-large`, 1024 dims, int8; Voyage `voyage-4` still supported) fused with RRF over two sources: the shared read-only `library.db` (open-access PMC, built offline: `pnpm corpus:fetch && pnpm corpus:build && pnpm corpus:push`) and cabinet PDF uploads (main DB, vector table partitioned by account). Child context sent to the model is pseudonymized (`child-context.ts`: no name, no free-text crisis notes; adds history, completed-test scores, a shortened latest report and non-identifying form dates, name redacted, capped at 5000 chars by `fitContext`). "Ask Amit" from an episode in progress (opens the bubble with that child and episode) sends that episode and the child's past crises, free-text notes included with the child's name redacted (`crisisContextText`), and asks for help automatically. Stored messages are the exact API content blocks, replayed unchanged.
- Privacy: public `/privacy` page (providers read from the server config); `PrivacyBadge` marks what is sent to the AI.
- Demo cabinets: three, fr / he / en (`demo@`, `demo-he@`, `demo-en@ergo-ai.app`; passwords `DEMO_PASSWORD`, `DEMO_HE_PASSWORD`, `DEMO_EN_PASSWORD` in `.env.local`), 4 realistic patients each, all text in the cabinet's language, fixed ids (`src/db/demo-ids.ts`), content in `src/db/demo/{fr,he,en}.ts`. **Every new feature must also give the patients of all three cabinets the new kind of data**, then `pnpm demo:seed` locally and `pnpm demo:push` to update production (`scripts/demo/push.sh`, all cabinets or `fr|he|en`; a new account-scoped table must also be added to `scripts/demo/account-sql.ts`, or the push refuses).
